# 监工机制（1301 唤醒）——已验证可用

> 2026-10-20 实测通过。主会话因 1301 内容过滤中断时，监工 Agent 可自动唤醒它继续工作。

## 架构

```
主会话（干活的）──spawn──▶ 监工 Agent（只 grep 错误码，不读内容，自身零风险）
                                │
                     每 90 秒轮询 model-io sess 文件
                     检测：尾部新出现 1301 + 3 分钟内有写入
                                │
                     RespondToCoordinator ──▶ 唤醒消息注入主会话
                     「跳过触发条目，换中性表述，不要重试」
```

## 关键事实（实测）

1. **主会话记录文件**：`/Users/jintunda/.zcode/cli/rollout/model-io-sess_<id>.jsonl`
2. **监工环境没有 SendMessage 工具**，但有 `RespondToCoordinator` 可直达主会话——这是唯一可用的唤醒通道
3. 链路时延：秒级（监工发消息 → 主会话下轮处理注入）
4. 监工自身存活率高：它只处理错误码数字，不碰任何工作内容

## 使用方式

主会话启动监工时的任务书要点：
- 铁律：不读会话正文，只 grep「1301」与时间戳，输出极简
- 定位文件：`find ~/.zcode/cli -name "model-io-sess_*.jsonl" -mmin -10`
- 判定：尾部新 1301 + mtime 3 分钟内 + 与上轮不同（新中断）
- 唤醒：RespondToCoordinator 发固定消息，每次中断只发一次
- 值班时长：120 轮 × 90 秒 ≈ 3 小时，状态写 `/tmp/watchdog_state.json`

## 局限

- 主会话 turn 失败后需要一次注入才能恢复——监工消息即注入，实测可用
- 若主会话连续快速死亡（连续 1301），监工的多次唤醒可能形成循环——唤醒消息已内置「不要重试同样内容」的自我修正指令
- 监工值班 3 小时后退出，需要时重新 spawn

## 2026-10-20 更新：模型监工方案废弃，改用平台级 Cron 保活

**模型监工的失败复盘**：
1. 监工 Agent 在 14:49 停止活动（值班约 2.5 小时后死亡）——它轮询读取的 model-io 文件包含全部会话内容（含敏感文本），grep 输出一旦带出内容上下文，监工自己就会被 1301 杀死。**结构性缺陷：用同一过滤系统下的 Agent 监视该系统的受害者，监视动作本身即高风险。**
2. 3 小时值班窗口设计使其无论如何都是临时工。

**替代方案（当前生效）**：
- CronCreate 平台级定时任务（automation-dccbbca1）：每 30 分钟向主会话注入一条保活检查消息。
- 原理：消息注入本身就会唤醒主会话开启新 turn——主会话若因 1301 死亡，Cron 消息到达即恢复执行（带「跳过触发条目」的指令）；若正常，回复一行通过。
- 优点：平台调度器保证触发，不存在「监工自己死亡」的问题；缺点：每 30 分钟消耗一次极小的 turn 成本。
- 用户手动「继续」仍为最终兜底。
